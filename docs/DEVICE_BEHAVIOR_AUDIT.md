# Audyt modelu urządzeń

Uzupełnienie: model obejmuje teraz również laptop, IoT/Raspberry Pi, NVR, mini serwer, UPS, pasywną szafę RACK oraz serwer RADIUS. Kontrola 802.1X/NAS nadaje VLAN przed DHCP i blokuje nieautoryzowane urządzenia niezależnie od ich ustawień IP. [Zakres, testy i ograniczenia AAA](./RADIUS.md). NVR i UPS mają parametry planistyczne, a RACK jest niezależny od topologii sieciowej.

Przegląd: 2026-11-12. Model rozszerzono następnie o [porty, interfejsy, media, PoE i diagnostykę](./PORTS_AND_DIAGNOSTICS.md). Sprawdzono wszystkie rodzaje z `Kind`, tworzenie urządzeń, topologię, adresowanie, DHCP, DNS, routing, ACL, NAT i dostępność usług. Wnioski dotyczą modelu aplikacji, a nie testów fizycznych urządzeń. Podstawę techniczną stanowią poniższe dokumenty producentów i RFC; wybór domyślnych usług i polityk pozostaje profilem aplikacji.

## Wyniki dla poszczególnych urządzeń

| Rodzaj            | Zachowanie w aplikacji i wynik przeglądu                                                                                                                                                                                                                                                                                                                               |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Internet          | Abstrakcyjny nadawca i cel spoza projektu. Skan wybiera skonfigurowane publiczne WAN/aliasy NAT. Nieznany prywatny adres nie jest już kierowany do Internetu. Dostępność nieznanego publicznego serwera i jego portów jest założeniem scenariusza, nie wynikiem pomiaru.                                                                                               |
| Router / firewall | Łączy L3, ACL, NAT i konfigurację DHCP. DNAT poprzedza filtrowanie celu; SNAT następuje po decyzji ACL. Odpowiedź konkretnego testu korzysta ze stanu połączenia. To przyjęty model zbliżony do [pfSense](https://docs.netgate.com/pfsense/en/latest/nat/process-order.html).                                                                                          |
| Router            | Łączy podsieci przez L3. Trasy connected mają zastosowanie także w trybie statycznym, a trasy użytkownika są wybierane po prefiksie i metryce. Rozpoznawane są adresy SVI, nie tylko główne IP urządzenia. Zasady routingu porównano z [RFC 1812](https://www.rfc-editor.org/rfc/rfc1812.html).                                                                        |
| Firewall          | Ruch przechodzi przez reguły w kolejności, a odpowiedź dozwolonego testu przez stan połączenia. Polityka domyślna i reguły są edytowalne. Porównano z [filtrowaniem stanowym pfSense](https://docs.netgate.com/pfsense/en/latest/firewall/fundamentals.html).                                                                                                          |
| Switch L2         | Przełącza wybrane VLAN-y zgodnie z łączami access/trunk, bez routingu. Poprawiono niezależność VLAN-u zarządzania od ruchu użytkowników. Działa także bez IP zarządzania; porównanie zasad [L2/L3 Cisco](https://documentation.meraki.com/Switching/MS_-_Switches/Design_and_Configure/Configuration_Guides/Layer_3_Switching/Comparing_Layer_3_and_Layer_2_Switches). |
| Switch L3         | Poprawiono przełączanie lokalnych ramek w L2 bez stosowania ACL routingu do ruchu wewnątrz VLAN-u. Komunikacja między podsieciami wymaga interfejsów L3/SVI i reguł routingu. [Cisco L2/L3](https://documentation.meraki.com/Switching/MS_-_Switches/Design_and_Configure/Configuration_Guides/Layer_3_Switching/Comparing_Layer_3_and_Layer_2_Switches).              |
| Switch prosty     | Przyjęty profil: jedna sieć dostępu, przekazywanie L2 bez IP zarządzania, routingu i lokalnych usług. Nie można go pingować ani wybrać jako serwer DHCP. Obsługa tagowanych ramek przez konkretne niezarządzalne modele wymaga dokumentacji producenta; aplikacja nie odwzorowuje wszystkich takich wariantów.                                                         |
| AP Wi-Fi          | Most bez NAT. Dodano niezależny VLAN klientów SSID, pozostawiając zgodność ze starszymi projektami. Uplink musi przenosić odpowiednie VLAN-y. Weryfikacja: [VLAN-y i zarządzanie AP Cisco](https://www.cisco.com/c/en/us/support/docs/wireless/aironet-1100-series/46141-vlanswireless.html).                                                                          |
| Serwer            | Zwykły serwer jest końcem komunikacji, nie routerem. Może udostępniać zadeklarowane usługi i DHCP po konfiguracji. Serwer DHCP bez własnego IP nie rozdaje adresów. Rola hypervisora uruchamia logiczny vSwitch dla gości.                                                                                                                                             |
| Maszyna VM        | Ma własny IP/VLAN oraz połączenie z wybranym hypervisorem. Brak hosta lub jego wyłączenie odcina komunikację. VLAN zarządzania hosta nie zastępuje VLAN-ów gości. Porównano z [konfiguracją VLAN Hyper-V](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/deploy/configure-virtual-local-area-networks-for-hyper-v).                           |
| Komputer          | Klient DHCP lub statyczny host; nie przekazuje ruchu innych urządzeń. Ruch lokalny wymaga L2, a zdalny bramy. Weryfikacja decyzji hosta: [RFC 1122](https://www.rfc-editor.org/rfc/rfc1122.html).                                                                                                                                                                      |
| Telefon           | Taki sam model hosta IP, z ikoną telefonu i domyślnym DHCP. Łącze do AP wskazuje logiczne podłączenie klienta. Brak radiowego zasięgu, WPA, roamingu i transmisji komórkowej; sam telefon nie jest hotspotem/routerem.                                                                                                                                                 |
| Drukarka          | Host z edytowalnymi usługami TCP/631 (IPP) i TCP/9100 (RAW). Doprecyzowano nazwy usług. Źródła: [IPP RFC 8010](https://datatracker.ietf.org/doc/html/rfc8010), [HP Jetdirect](https://h10032.www1.hp.com/ctg/Manual/c03478481.pdf).                                                                                                                                    |
| Serwer DNS        | Udostępnia UDP i TCP/53 oraz rekordy A. Dodano próbę TCP przy niedostępnym UDP i obsługę własnego resolvera lokalnie. TCP jest poprawnym transportem DNS — [RFC 7766](https://www.rfc-editor.org/info/rfc7766/).                                                                                                                                                       |
| Kamera IP         | Profil usług HTTP/HTTPS i RTSP TCP/554. Usunięto domyślny port 8000 jako rzekomo uniwersalny ONVIF. Porty producenta można dodać ręcznie. ONVIF discovery przez UDP/3702 i transmisja RTP nie są symulowane. Weryfikacja: [Axis — porty usług](https://help.axis.com/en-us/axis-os-knowledge-base).                                                                    |

## Poprawki wspólne

- DHCP rezerwuje wszystkie ważne dzierżawy przed obsługą nowych klientów; dodanie klienta na początek listy nie zabiera adresu innemu urządzeniu.
- Zmiana podsieci usuwa niedopasowane adresy automatyczne. Nowe są przydzielane wyłącznie po odnalezieniu osiągalnego serwera DHCP. Sama edycja VLAN-u nie tworzy adresu ani dzierżawy.
- Trasy connected SVI są uwzględniane również przy DHCP relay na routerze z routingiem statycznym.
- Ważna dzierżawa pozostaje podczas awarii serwera, odnawianie następuje od połowy okresu, a po wygaśnięciu bez odpowiedzi klient traci adres. Są to wybrane reguły [RFC 2131](https://www.rfc-editor.org/rfc/rfc2131.html), nie implementacja pakietów DHCP.
- Symulacja zgłasza konflikt aktywnych adresów IPv4 oraz statyczny adres spoza wskazanej podsieci, zamiast arbitralnie wybierać hosta.
- Odpowiedź używa adresu interfejsu, na który skierowano zapytanie, również dla SVI. ACL wejściowa nie jest stosowana do pakietu generowanego lokalnie jako do pakietu odebranego z innego urządzenia.

## Walidacja

`src/tests/deviceBehavior.test.ts` dodaje 43 przypadki: kompletność katalogu wszystkich 15 typów, przełączanie L2/L3, reguły i porty VLAN, adresy SVI, zachowanie hostów, profile usług, DHCP, SSID, DNS, konflikty i adresowanie. Istniejące testy obejmują NAT, routing, odpowiedzi, niedostępne usługi, VM, izolację gości i migrację projektów.

Dwa starsze scenariusze doprecyzowano: edycja podsieci sprawdza teraz rzeczywisty przydział przez DHCP; test braku routingu między VM jawnie wyłącza router. Przy działającym routerze i dozwolonych VLAN-ach taka komunikacja jest prawidłowa.

## Granice, które należy uwzględnić w projekcie

- Automatyczny routing korzysta z logicznej topologii. Nie oznacza działania OSPF/BGP ani automatycznego powstawania tras w fizycznym sprzęcie. Do sprawdzania własnych tablic służy tryb statyczny. Następny skok jest wskazywany jako sąsiad osiągalny w podłączonym L2 (również przez switch), bez rekurencyjnego rozwiązywania wielu tras do jego adresu.
- Jeden VLAN odpowiada jednej podsieci i jednemu wskazanemu urządzeniu bramy. Hosty mają wiele interfejsów z osobnymi maskami, bramami i DHCP. Brakuje nadal VRRP/HSRP, VRF oraz IPv6. Prefiksy katalogu LAN obsługują /1–/30, a jawne interfejsy IP /1–/32.
- Konfiguracja portów jest osobna na obu końcach, włącznie z native VLAN/PVID i tagowaniem. PoE ma model klasy/budżetu PSE/PD. Nie ma nadal tablic MAC/ARP, STP, LACP ani MTU. Pusta lista VLAN-ów zarządzalnego switcha oznacza brak dodatkowego ograniczenia poza konfiguracją łączy.
- AP obsługuje jeden logiczny SSID i VLAN klientów. Łącza klientów są wskazywane ręcznie; SSID nie zestawia ich automatycznie. VM może mieć wiele vNIC. Brak nadal oddzielnych wirtualnych switchy internal/private i SR-IOV.
- ACL routera i switcha L3 są bezstanowe; firewall oraz profil brzegu śledzą odpowiedź w obrębie jednego testu. Nie ma trwałego conntrack ani pełnego TCP, PAT z kolizjami portów, fragmentacji czy sesji równoległych. Pole WAN/LAN opisuje pochodzenie próby, nie konkretny interfejs wejściowy każdego urządzenia. Domyślne `deny` nowych urządzeń L3 jest świadomą polityką aplikacji, nie deklaracją fabrycznej konfiguracji każdego routera.
- Presety usług serwera/VM/drukarki/kamery są edytowalnymi przykładami. Brak uruchomionych systemów, autoryzacji, TLS i rzeczywistych aplikacji. Wartości trzeba dostosować do dokumentacji konkretnego sprzętu.
- DNS obejmuje rekordy A, bez rekursji, cache, TTL, delegacji, DNSSEC, EDNS i symulacji obcięcia odpowiedzi. DHCP nie obejmuje wymiany datagramów, wielu konkurujących serwerów, pełnego T2/rebinding, opcji wszystkich producentów ani trwałej bazy serwera poza projektem.

Diagram i wynik testów pozwalają sprawdzać zależności logiczne obsługiwane przez model. Potwierdzenie zachowania konkretnej instalacji wymaga jej konfiguracji interfejsów i usług oraz testów na sprzęcie lub w emulatorze systemów.
